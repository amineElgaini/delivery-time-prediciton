A few missing in a numeric column (like Delivery_person_Ratings) → impute with median
A few missing in a categorical column (like Weatherconditions) → impute with mode, or a new "Unknown" category if it's meaningful
A column with a huge chunk missing → might justify dropping it entirely
--------------------
Why .astype(float) and not .astype(int) for these: even though ages/ratings/counts look like whole numbers,
we haven't imputed missing values yet (still NaN in some rows) — and NaN can only exist in a float column,
not an int column. We'll convert to int later if needed, after imputation,
if a column truly has no decimals.

**Why `City`'s tiny "Semi-Urban" category (141 rows) matters:**

- With so few examples, the model can't learn a reliable pattern for it — 110ish rows in training, ~31 in test, is thin.
- **Linear models (Ridge, etc.):** may assign Semi-Urban a wildly off coefficient (e.g. ±20 min effect) just from noise in those few rows, not a real pattern.
- **Tree models (RandomForest):** may barely use it as a split at all — it contributes little.

**How to check later, with real evidence instead of guessing:**
1. Look at the model's coefficient for Semi-Urban — if it's way bigger/smaller than Urban/Metropolitan's, that's a red flag.
2. Filter test predictions to just Semi-Urban rows — if error is much worse there than other cities, it's struggling.
3. Train twice (with vs. without merging Semi-Urban into Urban) and compare RMSE — if merging doesn't hurt performance, it confirms merging is safe/better.

**Decision for now:** leave `City` as 3 separate categories. Revisit merging only if one of the checks above shows a real problem.

**How to compare coefficients (once you have a trained Ridge/linear model, in Step 3-4):**

1. **Extract them:**
```python
coefficients = pd.DataFrame({
    'feature': X_train.columns,
    'coefficient': model.coef_
})
coefficients = coefficients.sort_values('coefficient', key=abs, ascending=False)
print(coefficients)
```

2. **Compare within the same group.** `City` becomes `City_Urban` and `City_Semi-Urban` after encoding — compare their coefficients to each other, not to unrelated features.

3. **Look for a suspicious gap.** If `City_Urban = 2.3` but `City_Semi-Urban = 18.4`, that's a red flag — one city type shouldn't logically cause 8x more delay than a similar one.

4. **Check the overall scale.** If most feature coefficients sit around 1-6 minutes, but one jumps to 18+, that's the standout to investigate — likely noise from too little data (141 rows), not a real effect.
